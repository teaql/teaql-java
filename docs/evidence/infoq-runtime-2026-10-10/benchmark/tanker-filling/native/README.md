# Linux native-image experiment

This extends the matched six-launcher JVM experiment with actual Linux native compilation and the same isolated Merchant query/expression/update workload. Standalone classpath and JPMS are represented by one standalone native executable: the resulting program does not select between those two JVM launch modes at runtime.

The build uses Oracle GraalVM 21.0.12+7.1, GCC 14.2.0, x86_64 compatibility instructions, four compilation threads and an 8 GiB compiler heap. Build logs retain `/usr/bin/time -v` output. Builds are serial; build times are observations on this shared machine, not a controlled compiler benchmark. Functional checks and tracing-agent training can overlap a build. Timing campaigns run after all builds finish.

Spring Boot 3.2.0 uses its official SpringBootAotPlugin through Gradle, including compiled AOT sources, generated resources and generated proxy bytecode. Quarkus 3.8.3 exports `-Dquarkus.package.type=native-sources`, then its generated native-image argument file is used on Linux. Micronaut 4.3.14 uses its compiled bean definitions and bundled native-image features.

Initial attempts are preserved. The standalone image compiled and served `/version`, but its JDBC connection-pool initialization failed. Spring's initial executable failed to instantiate the XML-configured ConsoleAppender. The GraalVM tracing agent exercises schema setup, nonempty Q/E read, real writes to 49/48, readback and the empty weight query; the resulting metadata covers those observed paths. Machine-specific absolute log-resource entries are removed. PostgreSQL Driver constructor registration is added for the Quarkus service-loading path. Metadata is deployment integration, not a claim that an arbitrary application is fully reflection-free or that all possible paths are covered.

Quarkus's initial global `--link-at-build-time` rejected Hikari's absent optional Dropwizard metrics classes. The configured build retains strict linkage for `io.quarkus` and `io.teaql` and restores Native Image's service-loader feature for the manually constructed JDBC pool. It does not replace Hikari or TeaQL with a framework-specific database implementation.

Micronaut's initial native feature referenced `PropertyNamingStrategy.UpperCamelCaseStrategy`, removed in the pinned Jackson 2.22.3 dependency. Its `native-compat` Maven profile selects Jackson 2.16.1 across Jackson components. This dependency change is retained explicitly; a matching JVM control is required for a direct Micronaut JVM/native comparison. The original six-way JVM campaign remains unchanged. A further initialization failure required Netty, SLF4J and Logback runtime initialization, strict-image-heap, and exclusion of the broad Netty codec HTTP/HTTP2 build-time directives. The exact flags and failed log are retained.

The generated TeaQL domain and eight published TeaQL 1.554 artifacts are unchanged. Business code is the same ProbeOperations source, with execution logging disabled, explicit runtime/module installation, JDBC/Hikari connections and PostgreSQL SQL execution. The old Spring variant uses the existing 296/1.163 artifact and Spring AOT plus its observed reflection metadata. Its first compiled image failed on the actual query because package scanning found no SQL parsers. The final adapter explicitly registers the exact 17 shipped concrete parser classes, creating instances per repository, only in a native image. It restores WARN after legacy AOT logging initialization. This additional migration step is visible in the comparison.

`start-native.sh` uses the existing secret file on the server; no database credentials are retained here. Both native and JVM processes are given `-Xms128m -Xmx512m`, but their collectors and physical-memory behavior differ (Native Image Serial GC vs the JVM's default collector). Process RSS is measured from Linux `/proc`, not inferred from the configured heap limit.

`collect_native.py` preserves the JVM experiment's external clock, 20 ms readiness polling, first nonempty business read, first two writes, 10-second settling interval, randomized blocks, and separate fixed-warmup read/write campaign. Fresh processes do not mean cold OS caches. The completed campaign contains thirty startup runs and five load samples per accepted executable; no timing data from failed builds or failed business checks is included. Benchmark tests do not establish full-service migration, Android compatibility, production capacity, all database-failure rollback paths, or encrypted-ID/masking JSON behavior.

The hours=47 rejection is the adapter’s fixture guard. It does not test framework authorization or rollback after a database failure.
