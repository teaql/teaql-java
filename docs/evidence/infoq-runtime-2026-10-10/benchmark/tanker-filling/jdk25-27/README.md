# Java 25 / Java 27 extension

Track 1 reuses the exact six Java 21 bytecode bundles with Oracle JDK 25.0.4.1 and 27+35. This isolates runtime changes between25 and 27. Historical Java 21 used Amazon Corretto, so 21-to-25 observations also differ by distribution. Track 2 builds thin Java 25 wrappers on Spring Boot 4.1.1, Quarkus 3.40.1 LTS and Micronaut Platform 5.2.2 / Core 5.2.15, using the same published TeaQL 1.554 and domain/operation JARs. Each track has 30 randomized startup blocks and five fixed-warmup samples per accepted variant. Schemas, expected responses, heap flags, lazy ten-connection pools and measurement boundaries match the earlier experiments.

JDK 27 is GA (September 15, 2026). Vendor-documented support and observed compatibility are separate: Spring's current system-requirements page lists support through Java 26, so successful Java 27 checks are exploratory observations rather than vendor certification. GraalVM currently publishes25-series native tools; no Java 27 native result may be inferred from a 25 compiler. Native toolchain identity is recorded separately.

Official references: [Oracle JDK downloads](https://www.oracle.com/java/technologies/downloads/), [GraalVM downloads](https://www.graalvm.org/downloads/), [Spring requirements](https://docs.spring.io/spring-boot/system-requirements.html), [Quarkus releases](https://quarkus.io/releases/). Failed compatibility checks/builds remain evidence and are excluded from performance samples. Full original-service migration, Android, encrypted-reference JSON and database-failure rollback remain separate work.

Oracle’s script-friendly GraalVM 27 archive returned HTTP 404. The official GraalVM team also states that no JDK 26/27/28 releases are planned in [its release-train announcement](https://medium.com/graalvm/accelerating-the-graalvm-release-train-26b0d7cff2ab). Java 27 JVM observations and GraalVM25 native observations are separate categories.

## Build and measurement boundaries

The application source is branch `codex/java25-27-benchmark`, commit `3a29946`, in the tanker-filling-service repository. The new wrappers are under `upgrade/web-probes/java25/`. They were compiled with local Corretto 25.0.1; deployed processes use the separately recorded Oracle toolchains. Shared TeaQL and generated domain artifacts retain their Java 21 compatibility. Java 27 is a runtime comparison here, not a separate Java 27 source compilation.

Each Maven wrapper is built with a Java 25 `JAVA_HOME` and `mvn -f <wrapper>/pom.xml clean package`. Spring's native input additionally uses `spring-boot:process-aot package`; Quarkus uses `-Dquarkus.native.enabled=true -Dquarkus.native.sources-only=true`. Micronaut's platform version and annotation processor version are separate: platform 5.2.2 resolves core/processor 5.2.15. Old native-specific Jackson and Netty overrides are not carried into the new Micronaut build without an observed need.

On the authorized Linux host, `collect_jdk.py --runs 30 --load-repeats 5` runs the unchanged bundles through `start-jdk.sh`. After its post-campaign contract checks, `collect_current.py` runs the upgraded wrappers through `start-current.sh` with the same counts. Only after both JVM campaigns and their contract checks does `native25/run-native25.sh` train reachability metadata, compile serially, check each native deployment, and collect native observations. Credentials remain in a separate mode-600 environment file and are excluded from retained evidence.

`validate_results.py <batch>` recalculates statistics and audits sample counts and timed logs. `capture_provenance.py`, run after timing, verifies the eight shared TeaQL JARs, domain JAR and exact business-operation class bytes across the modern deployments. Native provenance additionally records compiler options, executable identities, build time and compiler peak RSS. Failed attempts are kept separately from accepted timing samples.

## Native initialization adaptation

The first Micronaut 5 native build failed because Netty's HTTP/HTTP2 embedded properties requested package-wide build-time initialization, producing Logback objects whose classes required runtime initialization. The retry defers Netty, SLF4J and Logback initialization and excludes those two broad Netty property files. It retains platform 5.2.2/core 5.2.15, Netty 4.2.19.Final and Jackson 2.22.3. The failed build log is preserved separately; no Jackson downgrade or business-code change is used for this retry. Baseline reachability configuration is reused where present and refreshed by the same checked workflow under GraalVM 25; metadata entry counts are not a measure of the compiler's total reflection registrations.

The legacy Spring/Redisson build also failed under GraalVM 25: the fixed reactive/RxJava class-name maps in `RedissonReference` contained `BiHashMap` objects whose type defaulted to runtime initialization. Retained `javap` output shows its constructor creates two ordinary HashMaps and the reference initializer fills them with fixed API class names. The retry marks `org.redisson.misc.BiHashMap` and `RedissonObjectBuilder$CodecMethodRef` for build-time initialization. The latter has an empty constructor and holds methods obtained for fixed API classes; its bytecode and a second failed build are also retained. The dependency closure and application configuration are unchanged. Its failed build remains in `native25/legacy/build-failed-redisson-initialization.log`.

The collectors' retained `environment.json` has a legacy single `jdk` field showing JDK 25. It is not a per-variant runtime field. The `-jdk25`/`-jdk27` variant suffix selects the corresponding recorded binary in the retained launcher; both actual toolchain versions and launcher hashes are in `build-provenance.json`. Raw environment files are preserved rather than silently rewritten.

GraalVM 25 agent output is retained in unified `reachability-metadata.json` files, including structured proxy/lambda entries. The standalone and legacy builds also retain classic baseline configuration as supplementary metadata. Provenance distinguishes fresh unified entries from those retained classic files. Reproduction requires access to the application branch and its project-local generated domain/operation artifacts; this package retains the measurement scripts, dependency identities, raw observations and build diagnostics.

The initial native batch `native25/results-20261010-121226` completed 150 startups but failed during Micronaut's first warm/concurrent load sample. Its first error was `Arena.ofShared` closure without `SharedArenaSupport`; subsequent reference-count errors were consequences. This partial batch is retained as failure evidence and excluded from accepted performance tables. Micronaut is rebuilt with `-H:+SharedArenaSupport` using the same dependencies, then every deployment runs the bounded workload as a smoke check before a fresh full campaign. The failure demonstrates why startup/read-write preflight alone is insufficient.

A separate three-start/one-load legacy diagnostic forced `spring.aot.enabled=true`. It did not remove the observed GraalVM 25 startup regression. Its one-second settle window and reduced counts are diagnostic only, excluded from the 30-start/five-load comparison. The regression is retained without an unverified causal attribution.
